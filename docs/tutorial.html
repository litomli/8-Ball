1. The big picture: what runs where

A web app is really three separate computers doing three jobs. Almost every confusing bug comes from mixing up which one you're writing code for, so start here.

ComputerJob in our appFiles
Browser (your laptop) Shows the page, handles clicks on the dropdowns components/match-form.tsx
Server (Vercel) Builds the HTML, runs our logic, is the only thing allowed to touch the database app/page.tsx, app/actions.ts, app/api/matches/route.ts
Database (Neon) Remembers the matches forever prisma/schema.prisma

The full trip when someone records a match:

You pick "Lynn beat Neo" and click the button
        │  (browser)
        ▼
recordMatch("Lynn", "Neo")        ← a Server Action: browser calls a function
        │                            that actually executes on the server
        ▼
db.match.create({ ... })          ← Prisma turns this into SQL: INSERT INTO matches ...
        │
        ▼
Neon stores a row                 ← now permanent; survives refreshes and redeploys
        │
        ▼
revalidatePath("/")               ← "that page is stale, rebuild it"
        │
        ▼
Server re-renders the history table and the leaderboard for everyone
Why the database can't be a file on the server The original plan mentioned SQLite (a database in a single file). On Vercel the server is serverless: it's created to handle a request and thrown away afterwards, so any file it wrote disappears. That's why the data lives in a separate hosted database that all the temporary servers share.

2. The five tools, and why each one exists

ToolPlain-English purpose
Next.js The framework. Turns folders into URLs, renders React on the server, and provides the plumbing between browser and server.
TypeScript JavaScript plus type labels. It catches mistakes like match.winnner while you type instead of at 11pm in production.
Tailwind CSS Styling by composing tiny classes (flex, p-6, text-sm) directly in the markup, instead of a separate stylesheet.
shadcn/ui Ready-made accessible components (Button, Card, Select, Table) that you copy into your repo and can edit — not an installed black box.
Prisma Lets you describe your tables once and then write db.match.findMany() instead of hand-writing SQL strings.

3. Step 1 — Creating the project

One command generates a working Next.js app. The flags just answer the setup questions up front: 

npx create-next-app@14 8-Ball --ts --tailwind --eslint --app --no-src-dir --import-alias "@/*"
  • --ts — TypeScript instead of plain JavaScript.
  • --app — the App Router: a folder named app/leaderboard/ with a page.tsx inside becomes the URL /leaderboard. No routing config anywhere.
  • --import-alias "@/*" — lets us write @/lib/db from any file instead of counting ../../.

Then the extra libraries this app needs:

npm install @prisma/client @radix-ui/react-select @radix-ui/react-slot \
            class-variance-authority clsx tailwind-merge tailwindcss-animate lucide-react
npm install --save-dev prisma

The middle group is what shadcn/ui components are built out of: Radix supplies the unstyled but accessible behaviour (keyboard navigation, focus handling) and Tailwind supplies the looks.

4. Step 2 — Designing the database

The most important design decision in the whole app: we do not store wins and losses. We store one row per match, and compute wins whenever someone asks.

prisma/schema.prisma
model Match {
  id        String   @id @default(cuid())
  winner    String
  loser     String
  createdAt DateTime @default(now()) @map(name: "created_at")

  @@index([createdAt])
  @@map(name: "matches")
}

Line by line:

  • @id @default(cuid()) — every row needs a unique name; cuid() generates a random one automatically, so we never invent ids ourselves.
  • winner/loser — text, e.g. "Lynn" and "Neo".
  • createdAt @default(now()) — the database stamps the time for us.
  • @@index([createdAt]) — a shortcut that keeps "newest first" fast even with thousands of rows, the same way an index at the back of a book beats flipping every page.
  • @@map — the table is called matches in SQL but Match in our code.
Why storing raw matches beats storing totals Totals are derived data. If you stored wins = 9 and a match was entered by mistake, you'd have to remember to decrement it, and any bug leaves the numbers permanently wrong. With one row per match, deleting the bad row instantly fixes every number on the site — and you get extra features for free (match history, head-to-head records, streaks) because the underlying facts are still there.

Running npx prisma db push reads that file and creates the real table in Neon. Prisma also generates a TypeScript client from it, which is why the editor knows match.winner is a string.

The four players aren't in the database at all — they never change:

lib/players.ts
export const PLAYERS = ["Thomas", "Cody", "Neo", "Lynn"] as const

export type Player = (typeof PLAYERS)[number]   // "Thomas" | "Cody" | "Neo" | "Lynn"

That second line is a neat TypeScript trick: the type is derived from the list, so if you add a fifth player to the array, every place that handles players type-checks against the new list automatically.

5. Step 3 — Talking to the database from code

The connection string is a secret, so it lives in an environment variable, never in the code:

.env (git-ignored — never committed!)
DATABASE_URL="postgresql://user:password@ep-something.neon.tech/neondb?sslmode=require"

.env.example is committed, with a fake value, so the next person knows which variables they need. On Vercel the same variable is set in the project settings.

lib/db.ts
import { PrismaClient } from "@prisma/client"

let prisma: PrismaClient
if (process.env.NODE_ENV === "production") {
  prisma = new PrismaClient()
} else {
  if (!global.cachedPrisma) {
    global.cachedPrisma = new PrismaClient()
  }
  prisma = global.cachedPrisma
}

export const db = prisma

Why the odd if? In development Next.js reloads your code on every save. A naive new PrismaClient() would create a fresh database connection each time until the database refuses more. Stashing one client on global — which survives reloads — keeps exactly one connection alive. In production the file loads once, so no trick is needed.

6. Step 4 — Server Components: pages that read the database

This is the part that surprises people coming from plain React: a page can be an async function that awaits the database, because it runs on the server before any HTML is sent.

app/page.tsx (trimmed)
export const dynamic = "force-dynamic"

export default async function HomePage() {
  const matches = await getRecentMatches()   // real SQL query, on the server

  return (
    <Card>
      <CardHeader><CardTitle>Match History</CardTitle></CardHeader>
      <CardContent>
        {matches.length === 0 ? (
          <p>No matches recorded yet.</p>
        ) : (
          <Table>
            <TableBody>
              {matches.map((match) => (
                <TableRow key={match.id}>
                  <TableCell>{match.winner}</TableCell>
                  <TableCell>{match.loser}</TableCell>
                </TableRow>
              ))}
            </TableBody>
          </Table>
        )}
      </CardContent>
    </Card>
  )
}

Three things worth pausing on:

  • No useEffect, no loading spinner, no fetch. The data is already there when the HTML is created, so the visitor never sees an empty table flash.
  • export const dynamic = "force-dynamic" tells Next.js "never cache this page as static HTML" — the scores change, so it must be rebuilt per request.
  • key={match.id} — React needs a stable id per row to update lists efficiently.

The query itself is one line, in a shared file so both pages can use it:

lib/matches.ts
export function getRecentMatches() {
  return db.match.findMany({ orderBy: { createdAt: "desc" } })
}

Prisma turns that into roughly SELECT * FROM matches ORDER BY created_at DESC.

7. Step 5 — The form and Server Actions (writing data)

Dropdowns need to respond to clicks instantly, so the form must run in the browser. That's what the first line declares:

components/match-form.tsx (trimmed)
"use client"

export function MatchForm() {
  const [winner, setWinner] = useState("")
  const [loser, setLoser] = useState("")
  const [message, setMessage] = useState(null)
  const [isPending, startTransition] = useTransition()

  function onSubmit(event) {
    event.preventDefault()                     // don't let the browser reload the page

    if (!winner || !loser) return setMessage({ type: "error", text: "Pick both a winner and a loser." })
    if (winner === loser) return setMessage({ type: "error", text: "Winner and loser must be different players." })

    startTransition(async () => {
      const result = await recordMatch(winner, loser)   // ← runs on the SERVER
      if (result.error) return setMessage({ type: "error", text: result.error })
      setMessage({ type: "success", text: `Recorded: ${winner} beat ${loser}.` })
      setWinner(""); setLoser("")
    })
  }
  ...
}
  • useState remembers what's selected; each setWinner re-renders the component.
  • useTransition gives us isPending, which is how the button can say "Saving…" and refuse double clicks.

recordMatch looks like an ordinary imported function, but look at the top of its file:

app/actions.ts
"use server"

export async function recordMatch(winner: string, loser: string) {
  const error = validateMatch({ winner, loser })
  if (error) return { error }

  await db.match.create({ data: { winner, loser } })

  revalidatePath("/")
  revalidatePath("/leaderboard")

  return { success: true }
}

"use server" makes this a Server Action. Next.js secretly replaces the import in the browser bundle with a network call, so calling recordMatch(...) from the browser executes this body on the server. The database password never leaves the server, and we didn't have to write any fetch code.

revalidatePath is the "throw away the cached version of this page" button — without it you'd submit a match and see a stale table.

Validating twice on purpose

The browser already blocks "Lynn beat Lynn", so why check again on the server? Because anything a browser sends can be faked (see the curl command in the next section). Browser checks are for friendliness; server checks are the real rule. Both call the same function so they can't disagree:

lib/matches.ts
export function validateMatch(input: MatchInput): string | null {
  if (!isPlayer(input.winner) || !isPlayer(input.loser)) {
    return "Winner and loser must both be known players."
  }
  if (input.winner === input.loser) {
    return "Winner and loser must be different players."
  }
  return null            // null means "no problem"
}
The one rule this app deliberately breaks Most apps check "is this person logged in?" before writing to the database. We skip that on purpose: the four players should be able to open a link and type a score. The trade-off is real — anyone with the URL can add matches — and it's acceptable because the stakes are pool bragging rights. Notice that "no login" is a decision, not something missing.

8. Step 6 — The leaderboard algorithm

The leaderboard turns a list of matches into a ranking table. We fetch every match, then tally in a single pass:

lib/matches.ts
export async function getStandings(): Promise<PlayerStanding[]> {
  const matches = await db.match.findMany({ select: { winner: true, loser: true } })

  // start everyone at 0 so a player with no games still appears
  const standings = new Map(
    PLAYERS.map((player) => [player, { player, wins: 0, losses: 0, played: 0, winRate: 0 }])
  )

  for (const match of matches) {
    const winner = standings.get(match.winner)
    const loser = standings.get(match.loser)
    if (winner) { winner.wins += 1; winner.played += 1 }
    if (loser)  { loser.losses += 1; loser.played += 1 }
  }

  return Array.from(standings.values())
    .map((s) => ({ ...s, winRate: s.played === 0 ? 0 : s.wins / s.played }))
    .sort((a, b) => b.wins - a.wins || b.winRate - a.winRate)
}

Details that matter more than they look:

  • select: { winner: true, loser: true } — ask only for the two columns we count. Don't move data you won't use.
  • Seeding the Map with all four players is why Neo shows up as 0-0 instead of vanishing before his first game.
  • s.played === 0 ? 0 : s.wins / s.played — dividing by zero in JavaScript gives NaN, which would render as literal "NaN%". The page shows an em dash instead.
  • b.wins - a.wins || b.winRate - a.winRate — a two-level sort. If the wins difference is 0 (a tie), || falls through to win rate as the tie-breaker.

One honest limitation: this loads every match to count them. That's instant for a pool league, but for a million rows you'd let the database do the counting with GROUP BY. Knowing when a simple approach stops being fine is most of engineering.

9. Step 7 — A JSON API for scripts

A file at app/api/matches/route.ts becomes the URL /api/matches. Exporting a function named GET or POST handles that HTTP method:

app/api/matches/route.ts
export async function GET() {
  return NextResponse.json(await getRecentMatches())
}

export async function POST(req: Request) {
  const body = await req.json().catch(() => null)

  const winner = typeof body?.winner === "string" ? body.winner : ""
  const loser  = typeof body?.loser  === "string" ? body.loser  : ""

  const error = validateMatch({ winner, loser })
  if (error) return NextResponse.json({ error }, { status: 422 })

  const match = await db.match.create({ data: { winner, loser } })
  return NextResponse.json(match, { status: 201 })
}

You can drive the live app straight from a terminal:

curl -X POST https://8-ball-ruby.vercel.app/api/matches \
  -H "content-type: application/json" \
  -d '{"winner":"Thomas","loser":"Cody"}'

Try sending {"winner":"Neo","loser":"Neo"} — you get 422 and an error message. That request never touched our dropdowns, which is exactly why the server validates. Note also the defensive typeof body?.winner === "string": a request can contain anything, including nothing at all.

Status codes are the conventions of the web: 200 fine, 201 created something, 422 your data was understood but unacceptable, 500 we crashed.

10. Step 8 — Putting it on the internet

  1. Database: create a free Neon Postgres project and copy its connection string.
  2. Tables: npx prisma db push with DATABASE_URL set, which creates the matches table.
  3. Hosting: import the GitHub repo into Vercel and set DATABASE_URL in the project's environment variables.
  4. Deploy: Vercel runs npm install then npm run build and publishes the result behind a public URL.

One small line in package.json makes step 4 work at all:

"scripts": {
  "postinstall": "prisma generate"
}

The generated Prisma client isn't committed to git (it's build output), so the build machine has to generate it after installing packages. postinstall is a hook npm runs automatically right after npm install. Without it the build fails with "@prisma/client did not initialize yet" — a very common first-deploy error.

Environment variables in one sentence Same code, different secrets: your laptop reads DATABASE_URL from .env, Vercel reads it from project settings, and the value is never in the repository — which is why leaking a password doesn't require changing code.

11. Step 9 — Backfilling old results (and a bug we fixed)

The league already had a season of history: Cody 7W-10L, Neo 2W-4L, Lynn 9W-6L, Thomas 8W-6L. But our table stores matches, not totals — so those numbers had to be turned back into 26 rows.

First, a sanity check that's really a piece of math:

total wins  = 7 + 2 + 9 + 8  = 26
total losses = 10 + 4 + 6 + 6 = 26   ✔ must be equal

Every match produces exactly one win and one loss, so those sums are always equal. The first version of the numbers came to 25 wins vs 26 losses, which proved one result was misremembered before a single line of code ran. Invariants like this are cheap and catch real errors.

Then a greedy pairing builds matches that satisfy every total:

prisma/seed-history.mjs (core idea)
while (winsRemain) {
  winner = player with the most wins still owed
  loser  = player with the most losses still owed (not the winner)
  emit { winner, loser }
  wins[winner] -= 1
  losses[loser] -= 1
}

Always spending the largest remaining counts first is what keeps the puzzle solvable — take from the small piles first and you can strand a player needing to beat only themselves. The script throws if the totals can't be realized instead of writing nonsense.

The bug an automated review caught

The first version inserted the 26 rows unconditionally. Run it twice and every row exists twice, so Cody's 7-10 silently becomes 14-20. Since ids are random, nothing in the database would stop it. The fix is to make the script idempotent — safe to run repeatedly: 

const existing = await db.match.count()
if (existing > 0) {
  console.log(`${existing} match(es) already recorded; refusing to seed.`)
  process.exitCode = 1
} else {
  await db.match.createMany({ data: matches })
}

This is worth internalizing: any script that writes to a real database will eventually be run twice — by a retry, a flaky connection, or a human who forgot. Design for the second run.

12. Try it yourself: 8 exercises

Roughly easiest to hardest. Every one of these is a real feature request you could ship.

  1. Add a fifth player. Edit PLAYERS in lib/players.ts. Nothing else changes — predict why before you try it.
  2. Show total matches played above the history table (matches.length).
  3. Sort the leaderboard by win rate instead of wins, and think about why 1-0 (100%) ranking above 9-6 might be unfair.
  4. Colour the win rate: green above 50%, red below, using Tailwind classes.
  5. Add a "current streak" column. Matches are already newest-first, so walk the list per player and stop at their first loss.
  6. Add a delete button for each match row — a Server Action calling db.match.delete, plus revalidatePath.
  7. Add a head-to-head grid: for every pair, how many times A beat B. All the data is already stored; it's pure counting.
  8. Add a score field (e.g. 7–5). This one touches everything: schema, prisma db push, the form, the table. That's what a "small" feature really costs.

Local workflow for all of these: npm install, put your DATABASE_URL in .env, then npm run dev and open localhost:3000. Run npm run lint and npm run build before pushing — that's the same check the deploy does.

13. Glossary

TermMeaning
FrameworkA pre-built structure for your app (Next.js) so you don't wire up routing, bundling and rendering yourself.
App RouterNext.js's folders-are-URLs system: app/leaderboard/page.tsx → /leaderboard.
Server ComponentA component rendered on the server; may read the database directly, ships no JavaScript to the browser.
Client ComponentA component marked "use client" that runs in the browser and can use state and event handlers.
Server ActionA function marked "use server" that the browser can call but which executes on the server.
ORMObject-Relational Mapper (Prisma): database rows as ordinary objects instead of SQL strings.
SchemaThe definition of your tables and their columns.
Migration / db pushApplying your schema to the real database.
Environment variableA configuration value supplied from outside the code, e.g. DATABASE_URL.
ServerlessHosting where a server is created per request and discarded after — fast and cheap, but with no permanent local files.
ValidationChecking data before storing it. Do it in the browser for kindness, on the server for safety.
IdempotentRunning it twice has the same effect as running it once.
Derived dataValues computed from stored facts (wins) rather than stored separately, so they can never disagree.
InvariantSomething that must always be true, e.g. total wins == total losses.
Cache / revalidateReusing a previously built page, and telling the framework when to rebuild it.
